# 09 · 存档容器格式 v1（一战斗一文件，多存档点追加）

2026-10-11 20:1x 用户裁定：换存档格式为"一个战斗只用一个文件，多个存档在里面"；追加高效、读取高效；**不兼容旧 `.hbs` 单存档文件格式**（新格式自立 v1，未来演进再谈兼容）；**不设存档点保留上限**（玩家手动清理）；读档语义默认"只读最新"（历史点选择 UI 后续再议）。

## 1. 动机与总则

- 现状：每次存档生成独立文件 `<64hex 指纹>_<日期>_<时间>.hbs`，同场战斗多次存档=多文件。
- 目标：单文件内追加多个存档点；追加成本 = 新快照数据 + 小索引重写（KB 级）；读取 = footer→索引→直跳任意存档点，无需解析其它点。
- **payload 完全复用现有 codec v8 编码字节流**：容器只管"多记录+索引"，每条记录的载荷就是现在写入单文件的那串字节；解码链（RestorePolicy_、结构界）零改动。

## 2. 文件布局

```
[Record 0][Record 1]…[Record N-1][Index][Footer(定长 32B)]
```

文件名：`<64hex 战斗指纹>.hbs`（去掉日期/时间/撞名序号后缀——一战斗一文件）。

### Record（每存档点一条，自描述、可独立校验）

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u32 | `'HBSR'` |
| payloadLen | u32 | 载荷字节数（现有 codec v8 编码输出） |
| crc32 | u32 | 载荷 CRC |
| payload | bytes[payloadLen] | codec v8 快照 |

定长头 12B + 变长载荷。

### Index（紧跟最后一条 Record；每次存档整体重写，KB 级）

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u32 | `'HBSI'` |
| count | u32 | 条目数 |
| entries | count × 24B | `{ offset:u64, payloadLen:u32, turn:u32, timestampUtcMs:u64 }`（4 对齐） |

### Footer（文件尾定长 32B，Little-Endian）

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u32 | `'HBSF'` |
| version | u16 | 1 |
| indexOffset | u64 | Index 区起始文件偏移 |
| crc | u32 | Index 区 CRC |
| reserved | u32 | 0 |

## 3. 追加写算法（存档）

1. 文件不存在 → 空文件，index 空表。
2. 读 Footer → indexOffset；旧 Record 区 = [0, indexOffset)。
3. 新 payload 编码（现有路径，不动）。
4. 打开（不开 tmp）：`SetFilePointer(indexOffset)` + `SetEndOfFile()` 截掉旧 Index+Footer → 顺序写 Record → 写新 Index（追加本条 entry）→ 写 Footer → Flush。
   - 追加成本 = payload O(n) + Index 全量（24B×条数，百条才几 KB）。旧索引被"挪后"，文件无垃圾区。
   - 崩溃安全：不用 tmp+rename（全量重写违背追加初衷）；恢复靠"索引可重建"（§5）。

## 4. 读取算法（读档）

1. 读文件尾 32B Footer：magic/version/crc 合法 → indexOffset → 读 Index（crc 校验）→ `entries[count-1]` → 按 offset 读 Record（magic/payloadLen/crc 校验）→ payload 交现有解码器。
2. 预留任意点访问：`entries[i]` 直跳，为将来存档点列表 UI 留好 API（`ContainerList`/`ContainerRead(i)`）。

## 5. 崩溃恢复（索引可重建）

写入顺序 Record→Index→Footer，任意时点崩溃：

- Footer 坏/缺失 → 顺序扫描 Record 流（magic+len+crc 逐条校验）重建 Index 与 Footer（"修复读"路径）；
- 中间 Record 半条 → CRC 挂，截断到上一条完整记录；
- 全部 Record 坏 → 空容器，等同无存档。

## 6. 改造点清单（实现轮）

1. `BattleArchive.inc.cpp`：写入改容器追加（§3）；读取改容器路径（§4）+ Footer 坏时修复读（§5）；列举（同指纹聚合）。
2. `BattleStoreService.inc.cpp`：文件名 `<指纹>.hbs`；同指纹文件存在即追加而非新建；`ParseGeneratedName` 相应简化。
3. 旧 `.hbs`（带时间戳名单）**不再出现在读档视野**（用户裁定"只认新格式"）；旧文件留盘不删。
4. 测试（`tests/ArchiveTests.cpp` 扩展）：空容器首写、多次追加、读最新、Footer 篡改后修复读、半 Record 截断、千点追加后的索引体积/读取耗时断言。
5. 保留策略：不设上限（裁定）；手动清理 = 删整个 `.hbs` 文件。

## 7. 风险与边界

- 同一指纹跨"重打同一场"（generation 变化）：容器按指纹聚合，重打后的存档点继续追加进同一文件——存档点自身带 generation 校验（现有机制），读最新即可，历史点可能属于旧 generation（列表 UI 上轮次时需展示 generation 区分）。
- 战斗指纹碰撞（理论极小）：现状同样存在，不因容器放大。
- 文件锁：与现状相同（游戏进程内独占写）。
