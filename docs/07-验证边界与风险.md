# 专题：验证边界与风险

> 来源：原《设计文档.md》§11–13、§16.7 阶段门、§15.3、未验收边界（2026-10-08 按用户裁定拆分）。

## 1. 动态验证门槛（原 §11）

### 1.1 首个原型

只实现无 UI 的同场内存内快照/恢复，使用调试热键或测试入口，禁止先实现跨会话和完整文件管理。每次实验都要保存恢复前后的字段摘要、资源引用计数、向量头和异常代码。

### 1.2 必测项目

1. 普通野战：损血、数量、站位、朝向、当前行动方；
2. 魔力、等待队列、已行动、反击和回合；
3. 法术持续、等级、士气、运气和英雄副本；
4. 投石车、弩车、急救帐篷、弹药车和箭塔；
5. 召唤、镜像、复活和永久死亡；
6. 障碍、火墙、地雷、攻城墙和双格单位；
7. 日志文本和两次恢复后的继续行动；
8. 单人随机序列：恢复后执行相同动作，结果与原路径一致；
9. 故意制造坏 CRC、过期场次、坏索引、缺失资源和非法槽位，确认只拒绝加载不崩溃；
10. 连续保存、连续读档、读档后再保存、读档后战斗结束，确认无泄漏、双释放或悬空指针。

### 1.3 通过条件

只有所有核心状态在至少一个普通野战、一个攻城战和一个包含召唤/镜像的战斗中通过，并且重复读档无崩溃、资源引用计数稳定、继续行动与原路径一致，才允许进入 UI 和跨会话阶段。任一核心项失败都不能用"从战斗开始重打"替代。

## 2. 已知风险与待验证问题（原 §12）

1. `+0x420` 自定义容器的元素语义和安全重建调用仍需动态确认。
2. 障碍向量在目标 exe 的实际向量头必须用内存断点确认；错误的头偏移会立即导致遍历崩溃。
3. `0x493FC0` 和 `0x495770` 的调用顺序及侧栏/日志重绘范围需实测。
4. 英雄副本除 `spellPoints +0x18` 外哪些标量会在战斗中持久改变需做前后差异采样。
5. `0x67FBE4` 与 TLS `+0x14` 是否在所有单人战斗路径同时读取需动态确认。
6. HD Mod、SoD_SP、打铁助手可能维护 BattleMgr 之外的状态；必须测试读档后自动战斗跟踪和快捷键交互。
7. 跨会话真实 `CALL_BATTLE` 调用点、参数布局和战前基线回滚仍未动态确认。
8. 资源加载失败、战斗中途对象数量变化和异常恢复不能依赖 SEH 兜底，必须设计可拒绝的前置校验。

## 3. 实施顺序（原 §13）

1. 建立目标 exe 指纹检查、日志和安全点观测，不写恢复内存。
2. 动态确认消息循环安全窗口、42 槽构造状态、障碍向量头、资源引用计数和 `+0x420` 容器。
3. 实现只读快照和一致性校验，输出调试摘要。
4. 实现同场恢复的准备阶段和最小部队/格子恢复；通过后逐项加入法术、英雄、攻城、障碍、日志和 RNG。
5. 加入失败拒绝、资源所有权检查、连续读档和压力测试。
6. 同场动态验收全部通过后，再实现二进制文件、索引和保留策略。
7. 文件读写稳定后接入悬浮条、下拉框、确认框和改键。
8. 最后研究跨会话重开路线；未通过独立验收前不开放跨会话读档。

## 4. 阶段门（原 §16.7 表）

| 阶段 | 实验/交付 | 放行判据 |
|---|---|---|
| P0 静态契约 | 函数ret/参数、字段宽度、资源所有权、RNG有效性、旧档策略 | 已核白名单、受控桥及障碍/部队/攻城原语；复杂资源已实现事务，仍须动态验收 |
| P1 只读时序 | 空闲/悬停/模态/动画/战术/自动/结算/重打/战略读档 | 外层安全窗口可重复，代际清理可靠 |
| P2 单动作差分 | 防御/等待/移动/近射/反击/士气幸运/单体群体魔法/英雄施法 | 所有逻辑变化归因；双侧施法和回合flags覆盖；随机调用轨迹完整 |
| P3 拓扑只读 | 死亡尸体/复活/召唤克隆/束缚魅惑/障碍火墙地雷/城墙机器箭塔 | 所有权/引用/构造清理配对，无悬空身份/越界 |
| P4 文件验证 | Capture→Encode→Decode比较；坏CRC/截断/重复段/错版本 | 白名单精确、失败零游戏写；不据此宣称战斗恢复 |
| P5 最小同场写 | 经明确授权先不变快照，再一个确定动作回退，不增删对象 | 标量/格/输入正确、正常退出；partial-write立即停实验 |
| P6 复杂同场 | 逐项增加拓扑/UI/连续读档，再走相同未来N步动作 | 状态+随机调用轨迹+伤害结果+战后结果一致，引用稳定 |
| P7 跨进程 | 战前战略基线→原版重建→身份重绑→恢复 | 结算一次，无重复经验/金币/伤亡；版本/插件不同拒绝 |

证据坐标及原始纠错统一记入 [战斗中存档可行性逆向笔记](D:/GitHub/H3/H3Note/战斗中存档可行性逆向笔记.md)。下一步在本地全新回归通过后，经授权以可丢弃战斗验证保存→移动/损血/等待→恢复→重复相同未来动作→正常结算，并扩展到召唤/克隆/清障/攻城的连续恢复；不据文件验证宣称资源重建已实机成功。

完整运行时通过条件仍以第 1 节为准；全量编译/独立测试不替代真实战斗验收。

## 5. 尚未解决（原 §15.3）

1. RNG 已采集游戏线程TLS+0x14和播种镜像；重复未来动作轨迹和第三方流仍未实机验收。
2. actionUndergoing/travelingSquares不作为忙碌门；messageResult==2只作取消条件，不能推导返回值为空闲。
3. 当前回滚限于编码比较不一致；任意SEH不保证回滚，写入异常或回滚失败以非继续异常停止进程。
4. serialized-equal 比较权威白名单及归一化后的悬停缓存，不证明动画/HD/其他插件状态和资源引用一致。
5. 原生日志滚动、侧栏和按钮、连续恢复与正常结算仍需要实机验证。
6. 当前在战前冻结恒定身份指纹，不因战中召唤/损血重算场次。跨进程与全部召唤场景的运行时恢复仍无完整验收证据。

## 6. 未验收边界（2026-10-07）

已有真实v6档只读自检，但新DLL的真机加载/恢复尚未测试。本地序列化相等与受控原语只证明编码和已测原语，不证明实际DEF/PCX加载、HD完整hook链、连续恢复资源引用、未来随机伤害、两种阴影开关画面、UI控制权、正常退出及战后结算全部正确。运行时完整恢复必须逐项满足第 1 节，不允许改文档为已成功。
