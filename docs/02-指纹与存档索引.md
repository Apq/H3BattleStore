# 专题：指纹与存档索引

> 以当前代码为准（`Entry.inc.cpp` 的 `BattleInitialFingerprint_/BattleFingerprint_/TryCaptureCombat_`、`BattleArchive.inc.cpp` 的 `ArchiveStore`）。历史设计沿革见[变更记录](../变更记录.md)。

## 1. 场次指纹

### 1.1 计算时机与冻结

指纹在 `0x462600`（战斗开始）HiHook 的**原版函数调用之前**由 `BattleInitialFingerprint_` 计算一次并冻结（`g_preBattleKey_` + `g_preBattleManager_`）。每场开始时 `BattleReset_` 先清空。此后保存/读档统一经 `BattleFingerprint_` 取冻结值，且要求当前 mgr 指针与采集时一致；否则报「未取得本场战斗的战前指纹，请重新进入战斗」。战中任何变化都不重算。

### 1.2 实际参与计算的输入

以下字段按固定顺序拼接后哈希；整数均为小端 4 字节。2026-10-08 用户最终裁定：地图身份只用标题，不加场景文件名（[BattleFingerprint.hpp](../modules/BattleFingerprint.hpp) 供生产与单测共用）：

- `u32 0x3250414D`（字节 `MAP2`，仅标题的地图身份方案标记，不是 codec 版本）；
- 地图标题/游戏名：`H3Main::mapInfo.mapName`（对象 `+0x1FB3C`，字符指针 `+0x1FB40`），编码为 `u32 字节长度 + 原始字符串字节`。该字段也用于 HD 游戏名/目录名，热座下可能是玩家输入的游戏名；
- 场景文件名不读取、不编码，也不保留文件名为空的占位字段；仅地图文件改名不影响指纹。同标题地图由既有战斗开局输入继续区分，不额外引入文件名；
- 只读已加载局的内存，不开磁盘地图/存档文件、不取地址值、不重编码。保留大小写、空白、颜色码及原生中文字节；空名编码长度 0，不替换为 `Unnamed`。不可读或字符串长度/容量/终止字节异常（要求 `Length()<=MaxLength()`，`Length()>0` 时还要求 `text[Length()]==0`）直接拒绝生成指纹，不以缺字段降级。标题采样上限 4MB，内容在堆上；

然后按原顺序追加以下战斗开局输入：

- 环境：`landType`、`specialTerrain`、`siegeKind2`（要塞等级，不是 +0x53A4 的可变门状态）、原始字节 `+0x53A8`、`+0x53A9`、`boatCombat`、`town` 指针空/非空（1/0）；
- 每侧（0..1）：`heroOwner`、hero 指针空/非空、前 7 个军队槽的 `army->type[slot]` 与 `army->count[slot]`（军队数据不可读直接失败，不降级）；
- 每侧英雄身份（v5 增补，指针不可读按 -1 编码）：`id`、`experience`、`level`、19 个穿戴槽 `bodyArtifacts[slot].id`；
- 城镇身份（v5 增补，不可读按 -1）：`number`、`type`、`owner`。

哈希用 Windows CryptoAPI `CALG_SHA_256`，输出 64 位小写十六进制。

刻意不加入：战斗实例随机值（2026-10-06 裁定不稳）、损血、站位、回合、障碍、自动施法标志等一切战中可变量。穿戴与英雄身份字段用于阻断"同色同阵容的不同英雄、穿戴不同强度不同"的互读。

### 1.3 开局时间核查（2026-10-08）

本轮在 SoD 的已加载局、原生存档头和保存/加载路径中，未确认到“创建这一局的时间”字段，暂不加入时间输入：

- `H3Main::date` 是当前游戏日/周/月，会随过天变化，不是开局时间；
- 场景浏览数据的 `FILETIME` 是文件时间，不是当前局身份，也不位于已加载 `H3Main::mapInfo` 中；
- NH3API 的 `cUniqueSystemID`（`H3Main+0x1F644`，32 字节）确实被原生保存/加载，但原生开局逐 DWORD 清首字节，HD 另有整段清零路径，不能将它当作开局时间或可靠的局唯一标识；
- 本次启动/读档时间、当前存档文件名或文件修改时间不加入：它们会使同一局重打/改名/重启后的指纹变化。

以后仅在确认某字段随战略存档序列化、同一局读档/重打/跨进程保持相同、重新开局生成新值后再接入。当前同一地图重新开局仍可能撞档；地图名不等于局唯一 ID。静态调查不证明所有游戏/MOD 都没有此字段。

### 1.4 撞档语义

地图标题及战斗开局输入完全相同则指纹相同、共用一份列表；恢复预检仍完整生效（撞档不豁免任何档案自身校验）。同标题地图、相同地图的两次开局仍可能碰撞，不宣称地图身份能隔离每一局。2026-10-08 地图身份从无到 `MAP1`（文件名+标题）再收缩为 `MAP2`（仅标题，用户裁定），每次输入变更旧档 key 均失配，文件保留在磁盘但不再出现在新列表；不做旧指纹回退匹配、迁移或删除。本次地图身份调整时 codec 仍为 v6、文件帧未改变；后续战争机器装备修复升级段内 codec 到 v7，不修改本节的战前冻结指纹规则。当前存档读取要求 v7。

## 2. 存档文件帧（双格式可切换：binary 与 json，2026-10-11 已实现）

2026-10-11 20:5x 用户裁定（取代"整体改 JSON"）：**存档格式做成可切换——现有二进制格式保留，新增 JSON 格式，由配置决定使用哪种**；读取也按配置只列举/读取对应后缀，两种后缀互不可见。默认 `binary`（现状行为不变）。JSON 后端彻底可读可手改可 diff；使用与 H3Auto 相同的 JSON 库（**nlohmann/json 3.11.3** 单头文件，复制入本仓库 `third_party/nlohmann/`，沿用 H3Auto `BattleStoreJsonCore.inc.hpp` 的 `JSON_NOEXCEPTION` 禁异常封装与 parse 签名）。扩展名随之 `.hbs → .json`（列举/校验同步改）。**JSON 格式版本从 1 起（`"version": 1`），后续演进自行递增，不沿用二进制 codec 版本号（2026-10-11 20:4x 裁定，取代此前"沿用不重置"）。**

结构草案（一档一 JSON 对象，与现有 8 段一一对应，缺一整档拒绝原则保留；`turn` 与文件名回合互为冗余校验）：

```json
{
  "format": "H3BS",
  "version": 1,
  "battleKey": "<64hex>",
  "timestampUtcMs": 1760000000000,
  "turn": 25,
  "sections": {
    "battle":   { "…mgr 标量/RNG 字段…": 0 },
    "stacks":   [ { "side": 0, "index": 0, "…42 槽数值字段…": 0 } ],
    "squares":  [ { "hex": 0, "…187 格字段…": 0 } ],
    "obstacles":[ { "…障碍字段…": 0 } ],
    "log":      [ "行1", "行2" ],
    "heroes":   [ { "…英雄副本标量…": 0 } ],
    "relations":[ { "…关系条目字段…": 0 } ],
    "spells":   [ { "…部队法术字段…": 0 } ]
  }
}
```

**字段级原子展开（2026-10-11 20:3x 用户硬约束）**：每个数据字段必须是真正的 JSON 属性（对象键或数组元素）——**禁止"一个属性里用分隔符（`,;|=` 等）塞多个字段"的伪打包**（如 `"stack": "0,1,15,20"` 不允许）；数组也只用于同构条目列表，条目内字段同为显式键。二进制原语不引入（无 base64/hex 包字节），枚举一律存名字符串或数值。

- 完整性判据：JSON 可解析 + schema 级字段校验（存在/类型/结构界）取代旧帧尾 CRC32；读档侧坏档防线（`RestorePolicy_`、解码结构界、障碍 preflight）原则不变，逐字段照旧生效。
- 原子写沿用 tmp + `FlushFileBuffers` + `MoveFileExW`。
- 已知代价（用户知情裁定）：体积约 3–10×（马拉松 10 万条日志档 ≈ 15–30MB）、编解码慢 5–20×（文本解析），换可读/可手改/可 diff。
**配置**：`user.ini` 新增 `saveFormat=binary|json`（默认 binary），读档/列举/存档三处同源判定；切格式=换后缀，不做格式间迁移/转换。
- 实现量：二进制 codec 原样保留；JSON 后端新增（段数据模型共用，双序列化后端）：`BattleCodec.inc.cpp` encode/decode 重写为 BattleJson 构建/取值（字段映射一一对应现二进制布局）；`BattleArchive.inc.cpp` 帧读写/扩展名/列举改 JSON；`BattleStoreService.inc.cpp` 同步；ArchiveTests 用 JSON 文本断言重写（含"无分隔符打包"的结构断言）。
- 旧平铺 `.hbs`、以及配置切到另一格式后写出的旧后缀档：留盘不删、不进当前配置的读档视野（同"不迁移"裁定；切回配置即可再见）。
- **实现与草案的差异（2026-10-11 落地时定案）**：`log` 段落盘为对象 `{"encoding": "acp"|"bytes", "lines": [...]}`——日志行是本机 ANSI（GBK），能严格转 UTF-8 的存 `"acp"`（真中文可读），转不动的按字节映射 U+0000..U+00FF 存 `"bytes"`（Latin-1 往返无损）；资源名 char[]（障碍 defName、塔 defName、城墙 wallPcxNames）同理按 Latin-1 映射存字符串。`heroes` 恒为 2 条（含未出场侧，`heroPresent:0`），warMachines 为 4 元素数组。**帧顶层无 `targetKey`/`sequence`**（生产恒为占位 64 个 `'0'` 与 0，读回按同值恢复），`turn` 只出现在顶层（battle 段内不重复）。非有限浮点（NaN/Inf）落盘为 `null`，读回 NaN 后照旧被 `RestorePolicy_` 拒绝——结局与二进制路径一致。dump 采用缩进 2 空格（`error_handler_t::replace` 兜底）。

## 3. 落盘与索引行为

> **2026-10-11 20:1x–20:2x 用户裁定（2026-10-11 21:11 已实现）**：存档改为按战斗指纹分目录组织，`自动`/`手动`分离；**两种格式（binary 与 json，见 §2）都落此布局，仅后缀不同**（多文件天然损坏隔离，曾评估的"一文件多存档点容器"方案因单点损坏连坐被否决，沿革见变更记录）。目录布局：
>
> ```text
> <存档根>\
>   <64hex 战斗指纹>\
>     手动\   <回合数>_<编号>.json|.hbs      ← 按 G 存档全部落此；一档一文件
>     自动\                                  ← 预留（本轮只建不写，用法后定）
> ```
>
> - 文件名 = `<存档时刻回合数>_<编号>`（2026-10-11 20:2x 追加裁定：**编号不限位数、不前补零**，自然位数）：编号为**同回合内存档序号**，从 `1` 起、取同回合已有最大编号 +1 递增，无上限；`(回合, 编号)` 唯一；文件名仅作标识与人工辨认。
> - **列表排序（2026-10-11 20:2x 用户裁定，取代"按 mtime 读最新"）**：进战场时把 `手动\` 下存档文件名加载进列表，按 **(回合数, 编号) 两段数值倒序**；比较必须把文件名拆成两段各自解析为整数比较，**禁止整串字符串排序**（否则回合/编号位数不同时字典序错乱，如 `7134_*` 与 `25_*`、`10` 与 `9`）。读档回退后回合数回跳（7134 回 25 再存）时，旧高回合档仍排在前——接受该语义。
> - 首次存档创建指纹目录并建齐 `手动/`、`自动/` 两个子目录；目录创建中断下次重建，无残留状态。
> - 旧平铺命名（`<指纹>_<日期>_<时间>.hbs`，及一切二进制 .hbs）的存量档**留盘不删、不进读档视野**（同"换格式不迁移"的一贯裁定）。
> - 实现（`BattleArchive.inc.cpp` 路径拼接/目录创建/编号分配/列举改 `手动\*.json|*.hbs` + `BattleStoreService.inc.cpp` 切换目标）与测试点（首存建树、同回合编号递增与跨回合重置、无上限自然位数（含 9→10、999→1000 解析）、两段数值倒序含 7134>25 与 25_10>25_2、旧平铺档不列举）见本节；UI/键位/流程不动。

- 文件名（新布局，2026-10-11 起生效）：`手动\<回合>_<编号>.json|.hbs`；编号按上节规则分配。文件名回合/编号仅是身份标识，列表身份以文件名为准（帧内 `turn` 与文件名互为冗余校验：JSON 档不一致直接隐藏；二进制档无帧内回合，以文件名为准）。
- 提交写入：先写唯一 `*.tmp` → `FlushFileBuffers` → `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 提交到唯一的新档名；不得覆盖旧档，不称为“原子替换”。任一步失败删除 tmp、不产生条目。`ArchiveStore::Save` 返回实际提交路径与 `(回合, 编号)`。
- 保存成功后按需回读刚提交的档案：Load + 校验 + 负载比较（二进制比逐段原始字节与 CRC；JSON 比解析后的文档树）+ 重新解码（`TryCaptureCombat_` 的 readback 阶段）；回读不过按 `persisted-unverified` 结束，不当成功。
- 列表扫描：逐个临时读取并校验文件，扫描结果仅保留 metadata（记录路径、battleKey、targetKey、时间和序号、回合、编号），不缓存所有档案 payload；点击读档时再按记录路径加载并校验完整内容。未知格式、段 id、坏 CRC、JSON 解析失败、帧内 turn 与文件名不符的文件从当前列表隐藏并写日志，但必须保留在磁盘，不自动删除。**排序按 (回合, 编号) 两段数值倒序**（取代旧的 timestampUtcMs/sequence 倒序；同回合内自然按存档先后排列）。
- 保留策略：所有档案永久保留，不执行每场条数或最近战斗场数的自动清理；编号为自然位数无上限，`(回合, 编号)` 唯一性即命名容量，不是档案保留上限。
