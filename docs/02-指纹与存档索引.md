# 专题：场次指纹与存档索引

> 来源：原《设计文档.md》§3（2026-10-08 按用户裁定拆分）。

## 1. 场次指纹

场次指纹只使用战斗开始时稳定的输入，不使用损血、站位、回合和当前行动状态。建议输入如下：

- 攻方/守方英雄身份及关键初始信息；
- 双方开局部队的生物类型、槽位和开局数量；
- 战斗发生的冒险地图坐标；
- 地形、攻城类型、城镇/城堡身份；
- 海战、特殊地形和其它能影响战场初始化的开局参数；
- 插件格式版本和目标游戏指纹。

使用固定字段顺序、明确字节序和长度前缀编码后计算 SHA-256（或目标编译环境中等价的稳定哈希）。指纹碰撞的处理与需求文档一致：如果两场开局输入完全相同，读回的战斗状态仍属于同一种初始场景；但索引必须记录最近使用时间，避免无关场景长期占用磁盘。

当前 v5 实现（`Entry.inc.cpp` 的 `BattleFingerprint_`）实际参与计算的输入：地形/特殊地形/攻城类型/护城河/水战/城镇指针空非空；每侧 `heroOwner`、`heroMonCount`、英雄指针空非空、前 7 军队槽的 `type/numberAtStart/slotIndex`；**每侧英雄身份（`id/experience/level`，指针不可读按 -1 编码）、19 个穿戴槽宝物 id（`H3Hero::bodyArtifacts[19]`，+0x12D）**；**城镇身份（`number/type/owner`）**。穿戴与身份字段阻断"同色同阵容的不同英雄、穿戴不同强度不同"的互读。刻意不加入战斗实例随机值（2026-10-06 用户裁定不稳）；重打与双胞胎守军碰撞由恢复预检的拓扑一致性比对兜底，需求文档中"撞档可接受"的结论相应收窄为"撞档仍须通过全部恢复预检"。任何指纹输入变更都会使旧档 key 失配（文件保留，列表不再显示）。

## 2. 存档元数据

每条记录至少包含：

```text
magic/version       文件格式识别与版本
battle_fingerprint  场次指纹（64 hex）
target_fingerprint  目标时刻指纹（当前占位全零）
created_at_ms       UTC 毫秒时间戳（文件名用其本地时间秒级表示）
sequence            保留字段（当前恒为调用方值，不再用于撞名）
sections[]          分段负载，各带 id/len/crc32
```

列表按 `created_at_ms + sequence + 文件名` 倒序显示。写文件采用临时文件写完、刷新并原子替换；列表每次直接扫描存档目录并验证每个文件，坏文件只从列表中隐藏并写错误日志，不让插件崩溃。
