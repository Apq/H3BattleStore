# 专题：存档容器格式 v1（一战斗一文件，多存档点追加）

状态：设计稿（待用户审定后实现）。2026-10-11 20:1x 用户裁定：换存档格式为"一个战斗只用一个文件，多个存档在里面"；追加高效、读取高效；不兼容旧 `.hbs` 单存档文件格式（新格式自立 v1，未来演进再谈兼容）；不设存档点保留上限（玩家手动清理）；读档语义默认"只读最新"（历史点列表 UI 后续再议）。

## 1. 背景与问题

- 现状（见 [06-文件格式与兼容](06-文件格式与兼容.md)）：每次存档生成独立文件 `<64hex 指纹>_<yyyymmdd>_<hhmmss>[_<撞名序号>].hbs`，同场战斗多次存档=多个文件；写入为全量 tmp+rename。
- 问题：①文件数量随存档次数线性增长，同场战斗的存档点散落、无聚合视图；②想要"回到本战斗较早存档点"必须人工辨认文件；③高频自动存档时全量重写路径无增量空间。
- 需求（用户原话）：一个战斗只想用一个文件（多个存档在里面）；能高效追加内容、比较高效读取。

## 2. 目标与非目标

**目标**
1. 单文件承载同场战斗的全部存档点，追加写入。
2. 读档 O(1) 定位：footer→索引→直跳目标记录，不解析其它存档点。
3. 载荷零重设计：每条记录的载荷就是现有 codec v8 编码字节流，解码链（RestorePolicy_、结构界、障碍 preflight）完全不动。
4. 崩溃可恢复：任意时点断电/崩溃后，容器可顺序扫描重建索引，已完整写入的存档点不丢。
5. 索引直跳 API 为"存档点列表选择 UI"预留（容器层支持按序号读任意点，本轮 UI 不做）。

**非目标**
- 不做旧 `.hbs` 单存档文件的读取兼容（用户裁定；旧文件留盘不删，读档视野只认新格式）。
- 不做存档点自动淘汰/压实（不设上限，玩家手动清理=删整个文件）。
- 不做载荷级压缩（沿用现状：载荷本身未压缩；日志包 LZMA 归档与本专题无关）。
- 不做多战斗合并/跨指纹聚合。

## 3. 备选方案与取舍

| 方案 | 追加 | 读取 | 崩溃安全 | 取舍 |
|---|---|---|---|---|
| A. 追加记录流（无索引，尾部倒链） | O(1) | 读最新需倒链回溯 O(1)，读任意点 O(N) | 尾记录可校验 | 否决：任意点访问弱，尾部定位逻辑脆 |
| **B. 记录+尾部索引+定长 footer（本设计）** | O(payload)+O(索引重写，24B/条) | O(1) 直跳任意点 | 索引可重建（§7） | **采用**：追加/读取/任意点三者兼得，索引 KB 级重写成本可忽略 |
| C. SQLite（WAL）单文件 | O(1) | 索引查询 | 事务级 | 否决：引入嵌入依赖，破坏单 DLL 零依赖形态；收益与 B 重合 |
| D. JSON/JSONL | 追加=重写或巨行 | 文本解析 5~20× 慢，体积 3~10× | 一般 | 否决（2026-10-11 20:0x 讨论裁定：追加优势在此场景为假，体积/速度全负） |

## 4. 文件布局（v1）

```
偏移 0                                                        文件尾
┌─────────┬─────────┬─────┬───────────┬─────────┬───────────┐
│Record 0 │Record 1 │ …   │Record N-1 │  Index  │ Footer32B │
└─────────┴─────────┴─────┴───────────┴─────────┴───────────┘
```

- 文件名：`<64hex 战斗指纹>.hbs`（去掉日期/时间/撞名序号——一指纹一文件）。
- 全部字段 Little-Endian。

### 4.1 Record（每存档点一条，自描述、可独立校验）

| 字段 | 偏移 | 类型 | 说明 |
|---|---|---|---|
| magic | +0 | u32 | `'HBSR'`（0x52534248） |
| payloadLen | +4 | u32 | 载荷字节数（codec v8 输出长度） |
| payloadCrc | +8 | u32 | 载荷 CRC32 |
| payload | +12 | bytes[payloadLen] | codec v8 快照字节流 |

### 4.2 Index（紧跟最后一条 Record；每次存档整体重写）

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u32 | `'HBSI'` |
| count | u32 | 存档点条数 |
| entries | count × 24B | 每条 `{ u64 offset; u32 payloadLen; u32 turn; u64 timestampUtcMs; }`（按存档时间升序，最后一条=最新） |

### 4.3 Footer（文件尾定长 32B）

| 字段 | 类型 | 说明 |
|---|---|---|
| magic | u32 | `'HBSF'` |
| version | u16 | 1 |
| indexOffset | u64 | Index 区起始文件偏移 |
| indexCrc | u32 | Index 区（含头）CRC32 |
| reserved | u32 | 0 |

## 5. 追加写算法（存档路径）

1. 文件不存在 → 视为空容器（count=0）。
2. 读 Footer（§6 步骤）取 indexOffset；Record 区 = [0, indexOffset)。
3. 走现有编码路径产出 payload（不动）。
4. 打开原文件（**不建 tmp**）：`SetFilePointer(indexOffset)` → `SetEndOfFile()` 截掉旧 Index+Footer → 顺序写 Record → 写新 Index（追加本条 entry）→ 写 Footer → Flush。
5. 追加成本 = payload O(n) + 索引重写 O(24B×count)。旧索引被"挪到"新数据之后，文件内无垃圾区。

## 6. 读取算法（读档路径，读最新）

1. 文件大小 < 32 → 空容器，等同无存档。
2. 读尾 32B Footer：magic/version 校验 → indexOffset/indexCrc。
3. 读 Index 区：magic/count/indexCrc 校验；count==0 → 空容器。
4. 取 entries[count-1] → 按 offset 读 Record：magic/payloadLen/payloadCrc 校验 → payload 交现有解码器。
5. 任意点访问（预留 API）：entries[i] 同法直跳。

## 7. 崩溃恢复（索引可重建）

写入顺序固定 Record→Index→Footer，任意时点崩溃后的表现与恢复：

| 崩溃点 | 文件状态 | 恢复 |
|---|---|---|
| Record 写一半 | Footer 仍指向旧 Index（旧视图完好） | 正常读=崩溃前的完整状态；修复读会扫出前面全部完整 Record |
| Record 完整、Index/Footer 未写 | Footer 仍是旧的 | 正常读=旧视图；修复读扫描发现新完整 Record，重建索引后新档可读 |
| Index/Footer 写一半 | Footer CRC 挂 | 触发修复读 |

**修复读**：Footer/Index 任一校验失败 → 从偏移 0 顺序扫描 Record 流（逐条 magic+len+crc 校验，半条截断），以完整记录重建 Index+Footer（就地重写一次），再走正常读。全部失败 → 空容器。

## 8. 接口与改造点（实现轮）

1. `BattleArchive.inc.cpp`：
   - 写入：`ArchiveAppendSave_(root, fingerprint, payload, turn, timestamp)`（§5）；
   - 读取：`ContainerReadLatest_(path, outPayload)`（§6）+ `ContainerReadAt_(path, i)`（预留）；
   - 修复：`ContainerRepair_(path)`（§7）；
   - 列举：按指纹聚合出容器文件（文件名即指纹）。
2. `BattleStoreService.inc.cpp`：存档目标改 `<指纹>.hbs`；同指纹文件存在即追加；`ParseGeneratedName` 简化为纯指纹名校验；带时间戳的旧名单从读档视野剔除。
3. 键位/流程/UI：不动（读档仍一键回最新点）。
4. 测试（`tests/ArchiveTests.cpp` 扩展）：空容器首写；连续追加 N 点读最新；任意点读取；Footer 篡改后修复读；半 Record 截断恢复；1000 点追加后的文件体积/读最新耗时断言；旧名单文件不被列出。

## 9. 风险与边界

- **重打同场战斗**（同指纹、不同 generation）：新存档点继续追加进同一文件；点自身带 generation 校验（现有机制），"读最新"天然正确；将来列表 UI 需展示 generation 区分新旧场次。
- **指纹碰撞**（理论极小）：与现状相同，不因容器放大；碰撞时表现为异场战斗互相追加，读档校验（战斗指纹一致性防线，保留）会拒绝。
- **超长马拉松**：10 万条日志档 ≈ 5–10MB/点，不设上限时千点文件可到 GB 级——玩家裁定接受（手动清理）；读取不随文件变大而变慢（直跳最新点）。
- **文件锁**：游戏进程内独占写，与现状相同。
- **与验证边界的关系**：本专题只改"容器/文件层"；采集、编码、解码、恢复防线、验证边界（[07](07-验证边界与风险.md)）全部不变。
