# 专题：快照模型与采集

> 来源：原《设计文档.md》§4、§5、§16.1–16.3（2026-10-08 按用户裁定拆分）。
> 采集语义以本文与 `BattleCapture.inc.cpp` 为准；恢复侧契约见《04-恢复事务与校验》。

## 1. 内存快照模型

快照只由可序列化值、身份索引和文本组成。任何字段若是游戏地址、资源指针、vtable、容器头或瞬态局部变量，都不能直接落盘。

### 1.1 BattleMgr 数值区

目标管理器为 `*(H3CombatManager**)0x699420`，静态大小 `0x140EC`。按照字段白名单保存：

- 动作参数：`+0x3C..+0x48`；合法保存点必须为空闲动作；
- 回合、战术阶段、等待阶段、完成标志和当前行动方；
- `squares[187]`（起点 `+0x1C4`，每项 `0x70`）以及可达格缓存；
- 地形、特殊地形、攻城类型、城墙生命和城墙存活数组；
- 双方英雄施法能力、已施法标志、召唤/镜像相关标量；
- 箭塔和战争机器所需的纯数值字段；
- 必须在等待帧一致的鼠标/重绘标量。

以下字段只在运行时重绑，不进入负载：

- `hero[2]`、`army[2]`、`mapitem`、`town`、`dlg`、`activeStack`；
- 背景、城墙 PCX、英雄/箭塔/生物 DEF、WAV、动画对象；
- 所有 vtable 和指向游戏堆的地址。

### 1.2 42 个部队槽

部队起点为 `mgr + 0x54CC`，单槽 `0x548`，两侧间距 `0x6EE8`，共 `2×21`。每槽快照保存：

- 身份和位置：类型 `+0x34`、位置 `+0x38`、朝向 `+0x44`、side `+0xF4`、sideIndex `+0xF8`、slot `+0x5C`；
- 数量和生命：numberAlive `+0x4C`、healthLost `+0x58`、numberForeverDead `+0x54`、numberAtStart `+0x60`、baseHP `+0x6C`；
- 行动：已行动、反击次数、走过格数、等待标志以及相关回合值；
- 法术：active spell、`+0x198` 的持续回合数组、`+0x2DC` 的等级数组、`+0x458..+0x4D4` 效果缓存；
- 克隆和召唤身份：clone id、持续回合、召唤标志；
- 士气/运气的最终数值和可确认的派生字段；
- 战争机器类型和箭塔数值。

`type == -1` 是空槽判定。以下内容不保存为裸地址：

- `def +0x164`、`shootingDef +0x168`、8 个 WAV `+0x170..+0x18C`；
- 动画及效果对象；
- 4 个指针向量头 `+0x4F4/+0x504/+0x514/+0x524`；
- `+0x420` 附近的自定义容器头；
- `info +0x74` 中需要由目标战斗资源重新绑定的内部资源地址。

### 1.3 容器与关系

确认的四个部队向量保存 `H3CombatCreature*` 裸指针。快照元素使用稳定身份 `(side, slot)`，恢复后映射为当前槽地址。不得保存 `m_first/m_last/m_capacity`。

`+0x420` 不是 `H3Vector`：构造函数初始化 `+0x424..+0x440` 八个 dword，重置函数传给 `FUN_00448A80 @ 0x448A80`。元素语义和生命周期仍是动态原型门槛，设计实现不得把它当普通 vector 处理。

BattleMgr 侧：

- `eagleEyeSpell` 保存值元素；
- `obstacleInfo +0x13D5C/+0x13D60/+0x13D64` 按真实向量头读取，元素为 `H3Obstacle` 值；
- 障碍 `def` 和 `info` 用类型/静态表身份表示，不能存指针；
- `H3CombatDlg::combatText +0x54` 保存每条 `H3String` 的文本，不保存 `H3String*`。

### 1.4 英雄副本与随机

每场战斗创建两个 `0x492` 字节、`/Zp1` 对齐的战斗英雄副本。保存：

- `spellPoints +0x18`（`INT16`）；
- codec v7 新增英雄存在标记、战争机器穿戴槽13–16的完整 ID/subtype（各8字节，两侧共8条）；机器死亡会移除对应装备，不属于战中恒定数据。弹药车宝物5决定射击是否免扣弹，不能仅恢复死/活部队而遗漏装备；
- 剩余弹药 `stack+0xD8` 已由 `infoCombat[6]` 保存；本轮不增加重复弹药字段；
- 不保存副本中指向地图资料、法术书或资源的内部指针。

单人模式保存两处 RNG：TLS 单例 `+0x14` 和镜像全局 `0x67FBE4`，二者不随rand同步推进，必须分别保存（2026-10-06 起已采集）。当前尚无 rngValid/线程角色标记，恢复提交时机与随机消费调查见《04-恢复事务与校验》的 RNG 恢复契约。多人 `0x50B3C0` 含timeGetTime路径，首阶段排除。

## 2. 保存流程（当前链路，`TryCaptureCombat_`）

1. 输入侧先过共享时机窗口 `CombatStorageWindow_`（见《05-UI与输入》第 5 节）：不在窗口内静默丢弃，不排队。
2. `CombatCanCapture_` 再做防御性复查：管理器可读、非 finished、非 autoCombat；尾部 action/actionUndergoing 不作忙碌门（H3API 布局错位说明见《04-恢复事务与校验》）。
3. `CaptureBattle_` 游戏线程只读采集白名单数值；资源地址转身份。采集完成后 `CodecInvalidateHover_` 剔除悬停意图。
4. 取战前冻结指纹（见《02-指纹与存档索引》），`CodecEncode` 编码 8 段，`timestampUtcMs=now`、`sequence=0`、targetKey 全零占位。
5. `ArchiveStore::Save` 写入唯一 `*.tmp`，`FlushFileBuffers` 后以 `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 提交为新的唯一档案，不覆盖旧档、不称为原子替换；不执行任何档案清理，返回实际提交路径（含同秒撞名后缀）。列表索引只保留 metadata，完整 payload 按需读取。
6. 立即回读该文件：CRC、逐段原始字节比较、重新解码；回读不过按 `persisted-unverified` 结束，不显示成功。
7. 成功后 `UiMarkSaved_` 标记"已存档"时间戳并重绘常驻列表（新档天然居首）。
8. 任何一步失败不新增条目并提示；保存全程不调用战斗重算函数、不修改战斗内存、不触发 Refresh。

## 3. 生命周期与状态边界（原 16.1）

已确认的形态是 **长驻管理器 + 按场创建的会话资源 + 战略输入/结算回写 + 外部随机/插件状态**，不是每场独立分配一个完整内存块。

- S：全局初始化分配 `0x140EC` 管理器并调用 `0x462340`，同时构造 42 个内嵌槽；退出一场不代表管理器地址改变。
- S：`0x462600` 建立本场 `0x8C` 主 dlg，`0x471D20` 构造、`0x602970` 注册；`0x462E40` 通过 `0x602A60` 摘链、虚析构并清 `+0x132FC/+0x13300`，释放本场 `+0x53AC/+0x53B0/+0x53B4` 绘图资源。
- S：`0x4AEBD0` 创建战斗英雄副本；`0x476DA0` 是战略回写/结算调查边界。地图英雄、army、town、mapitem 既可能是输入，也可能是结果接收者，不能一律归为战斗拥有。
- H：`0x4AD160` 栈局部变量、HD/第三方全局和 TLS 是否在等待输入后仍参与未来结果，需要读写追踪。不能保存 CPU 调用栈并跨进程恢复，必须找到逻辑状态可闭合的外层边界。

场次身份应由 `battleGeneration + 主dlg创建/销毁事件 + 战前稳定指纹` 组成；代际用于丢弃本进程过期请求，指纹用于重新进入后的档案匹配，二者不能互相替代。相同地址被复用也必须形成新代际。

## 5. 如何在内存找全（原 16.3）

1. **固定环境。** 记录目标EXE哈希、基址、HD版本、已加载模块和插件配置；复制测试地图/战略基线，离线单人。不得以玩家正式战斗作破坏性实验。
2. **沿生命周期采样。** 战斗入口前、装配后、初始化后、首个等待帧、每个动作完成、结算前、清理后各取只读样本；同时记manager/dlg/hero/army地址与代际。用构造/清理调用归因owned/borrowed/refcount，不靠地址邻近判断所有权。
3. **建立三类差分。** A连续空闲无输入；B单个确定动作前后；C纯悬停/模态开关/动画。先识别时间/帧/容量噪声，再归一化指针为身份；原始dump仅供分析，绝不整块写回。动作/代际在读取前后改变则丢弃样本；必要时调试器短暂停线程取一致样本。
4. **有界指针图。** manager、hero/army、dlg、WindowManager为根，深度2–3、节点/字节上限、已提交可读页检查、环检测；分别处理静态表、借用对象、拥有容器、引用资源。vector按元素、deque按0x1000块读取；不盲扫全堆或碰不可读页。
5. **硬件写断点轮换。** x86通常4个槽，从action、numberAlive、healthLost、mana开始，按1/2/4字节对齐轮换；记录线程/EIP/调用栈/动作ID/旧新值。对象释放后撤销；再对未知逻辑变化区查读点，以"未来是否消费"判定是否入快照。
6. **外部闭包。** 追 `0x4AD160/0x4AEBD0/0x4635D0/0x462600/0x476DA0/0x462E40`；查战斗链对mgr以外全局、堆和栈的读写。特别记录随机、金币/军队/英雄、结果、HD/插件接口。拒绝把旧WoG `0x75AE24/0x75AEB0/0x75ACDD` 直接迁到SoD。

优先用外部调试器/读进程工具，不先加侵入Hook。后续只读探针采用预分配定长ring、丢样计数，记录阶段与归一化CRC；不得在rand/每帧高频路径分配、同步写盘或遍历全容器。不要整manager PAGE_GUARD、改页保护或全堆单步，防止观测改变时序。
