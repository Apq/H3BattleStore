# 专题：恢复事务与校验

> 来源：原《设计文档.md》§6、§7、§16.4–16.8（2026-10-08 按用户裁定拆分）。
> 当前实现以本文「当前代码核查缺口与放行现状」「v5 可逆对象与资源事务」为准；实际代码顺序见 `BattleRestore.inc.cpp` 的 `RestoreSameBattle_`。

## 1. 同场恢复流程（历史设计约束，原 §6）

同场恢复是第一阶段候选路线。以下为历史设计约束，不是当前实现保证；当前只放行本文下半部的白名单及已确认障碍重建，不执行下列历史部队资源重建。新的所有权顺序和放行阶段门见本文第 3、4 节及《07-验证边界与风险》，安全窗口须先动态确认。

### 1.1 安全入口

`0x473A00` 是 `H3CombatManager::ProcessMessage`，只处理一条消息，不证明队列已空。原HiHook函数须在SEH之外恰好调用一次；返回2仅用作当前保守结束拒绝信号，不推导"其余返回值安全"。检查未结束/非战术/移动格/动画/自动/顶层dlg及场次代际后，还须动态证明这是外层等待边界；action四元组不能简单全零判定。不得在 `0x4746B0` 输入翻译、`0x4786B0` 执行器、AfterBlt、动画回调或模态内部恢复。

如果安全点无法动态确认，插件只拒绝读档，不冒险写内存。SEH 只能记录异常和中止本次提交，不能把错误的对象所有权或半恢复状态自动变正确。

#### 2026-10-10 玩家日志：点击读档后持续红灯（诊断完成，补丁未实现）

玩家日志包 `H3BattleStore_logs_20261010_103209.7z`（SHA256=`C99127F54DE73A75926528F13D3CB86BF9FD3285C517F8692F9E67CBD3AF304A`），自报 v0.6.2026.1009 / battle-diag-ammo-equipment-v7 / codec7。五份日志仅09:56会话出现四次Load queued：10:07:02 gen21、10:09:31 gen25、10:14:17 gen33、10:26:28 gen65。前三次结束战斗仍pending_load=1，分别等待121.160、190.930、36.125秒；最后观察到日志结束跨度340.540秒。未见kind=load、load.confirm或serialized-equal；这是排队未执行，不能描述成恢复成功后红灯，也没有文件损坏或Codec拒绝的证据。完整证据及SoD调用链见 [逆向笔记§10.18](<../../H3Note/战斗中存档可行性逆向笔记.md>)。

当前 [消息钩子](<../modules/Entry.inc.cpp#L679-L727>)只在原函数返回且全局g_messageDepth==1时处理请求；[RestoreWindow_](<../modules/BattleRestore.inc.cpp#L154-L157>)重复要求1。[UiProcessRestore_](<../modules/BattleUi.inc.cpp#L1266-L1278>)的五秒超时取消也在同一入口内，故深度大于1时超时维护不可达。日志普通输入深度逐渐从1到6，升阶与item2003战斗选项消息未返回期间出现新战斗相伴；具体是谁重开循环尚无证据，不能归责某插件或断言finally漏减。pending使灯红并拒绝保存/再次读档，与真正执行安全谓词不检查pending并不矛盾。

候选修复分两步：先拆出纯pending维护，在战斗线程每帧/每条消息、不受可恢复深度和窗口提前返回阻断地取消超时/失代/结束请求，日志记录一次原因与age，解除永久挂起；再按入口generation、manager、dialog和帧身份辨认当前战斗有效消息的最外层返回边界，排除旧代祖先但保留同场嵌套、主对话框、玩家活栈、action/executor/spell门禁。旧帧不得消费新代请求，祖先返回后的旧局部状态影响仍待验证。不得简单删depth限制或在Reset清零计数，也不能把真正恢复搬到Cycle/Blt：原生0x473A00入口自身调用Cycle，帧回调可能仍在原函数内部。无法确认写入安全点时明确取消，不强制改灯绿。

本次仅分析并记录方案，未修改生产源码、未构建/部署或运行游戏。未来单元回归需覆盖无消费入口仍能超时、跨代消息帧归属、同场嵌套拒绝、旧帧返回、确认取消/结束及请求恰好一次；普通战斗/连续选项重打/连续读档后的恢复与保存由用户实测。

#### 2026-10-10 修复实现（v0.7 / battle-diag-restore-boundary-v8）

1. `BattleInputPolicy.hpp` 新增纯策略：`BattleRestoreMaintainDecision_`（排队请求超时/换场/结束取消，>5000ms 严格大于，换场与结束优先于超时）与 `BattleMessageFrames_` 栈上 POD 帧栈（Enter/Leave/Depth/Boundary）。每个 `Hook_CombatMessage_` 调用一个栈帧，记录进入时场次与管理器，对话框在首次确认可读时补全；原函数返回后置 `nativeReturned`，finally 出栈。
2. `RestoreWindow_` 消费边界由绝对 `g_messageDepth==1` 改为 `g_messageFrames.Boundary(当前场次, mgr, mgr->dlg)`：只认“当前战斗自己的最外层消息帧且原函数已返回”。旧场未退栈祖先帧按场次归属不计数不判定（修复玩家 depth 3..6 饥饿）；同场真实嵌套（>=2，当前战斗内再开选项框）仍拒绝；管理器/对话框身份在返回后重新核验，mgr 地址被新场复用或对话框被替换都拒绝。换场不清零帧栈，旧帧 finally 出栈即消失；全局 `g_messageDepth` 保留仅作诊断。
3. `UiMaintainRestore_` 每帧在 `CombatCycleAfter_` 顶部调用（先于 busy/fatal/主对话框提前返回）：超时（>5s）、换场、战斗结束取消排队并写 `[Load] cancelled reason=… age_ms=… depth=… battle_depth=… window=…`；超时另给非模态提示“读档等待超时，已取消；请重试”。维护只清队列状态，不写战斗内存。
4. `[Load] queued` 与 `[Command]` 日志补充 `battle_depth`，玩家日志可直接区分“绝对深度被祖先抬高”与“当前场真实嵌套”。

验收：LogControls 新增纯策略回归（旧场祖先不计数、原函数未返回非边界、同场嵌套拒绝且解栈后恢复、manager 复用/对话框替换/空对话框拒绝、>5000ms 与恰 5000ms 严格性、换场优先超时），三套件实跑全部通过；`build.bat /t:Rebuild` 全量 0 错误 0 警告。游戏内连续选项重打→读档、读档后立即保存、确认取消仍由用户实测；祖先帧存活期间执行恢复的安全性以实机日志复核，未做 ABI 探针。

### 1.2 两阶段提交原则

恢复分为"准备"和"提交"：

- 准备阶段验证文件 CRC、游戏版本、场次指纹、所有槽位身份、容器索引和资源类型；
- 提交阶段尽量使用原版构造/重置函数，完成后重新验证关键不变量；
- 在提交前保留运行时资源身份和容器快照。若发现准备条件不满足，完全不写战斗内存；
- 对已经调用析构/解引用的失败路径，不能假定简单 `memcpy` 可以回滚。实现必须提供逐步清理和重新构造路径，或在首个可安全点直接拒绝加载。

### 1.3 恢复顺序（历史候选）

1. **校验活动战斗和快照。** 验证当前 BattleMgr、对话框和槽位地址仍属于本场；验证不是结果/结算帧。
2. **记录资源边界。** 私有记录当前槽位的 DEF/WAV 身份、向量元素、障碍条目和日志内容；不复制容器头。
3. **固定槽位不销毁。** BattleMgr 构造函数 `0x462340` 使用 `0x6181FA(0x548, 42, 0x43CF70, 0x43D120)` 统一构造 42 个槽。中途恢复不得重新批量构造、析构或释放槽位本身。
4. **清理快照中不存在的部队。** 对当前存在但快照为空的槽使用 `0x43D2E0` 重置。不得直接 `free` DEF/WAV。
5. **创建快照中新增的部队。** 对当前为空但快照存在的槽使用 `0x43D5D0`，由内部 `0x43D450` 加载生物资料和资源，再登记格子和基础关系。不得先写旧资源指针。
6. **清理并重建关系容器。** 四个裸指针向量释放自己的缓冲并以 `(side, slot)` 重建；元素对象不由这些向量释放。`+0x420` 必须走 `0x448A80` 的原版容器操作，直到动态确认元素语义前不得猜测写入。
7. **恢复 BattleMgr 和槽位纯数据。** 跳过 vtable、资源指针、对象指针、向量头和自定义容器头，回写格子、动作/回合、数量、生命、站位、法术、攻城、城墙和战争机器数值。
8. **处理引用计数资源。** 同类型槽保留原资源；类型变化时使用资源管理器/原版加载路径取得新对象，按 `H3ResourceItem +0x18` 增加引用，再对旧对象调用虚表 `+4` 解引用。禁止直接 `delete` 或 `free`。
9. **重建障碍。** `0x466710`删除旧障碍会改格子，必须早于最终squares回写；def==NULL条目不能盲调原释放，需先核实其墓碑/清理语义。取得正确DEF引用及静态info后再重建数值/index映射。`+0x13D58`是vector对象起点，元素指针头才是 `+0x13D5C/+0x13D60/+0x13D64`；二者不是矛盾地址。此步优先级纠正历史第7步顺序，整体以本文「如何恢复内存」为准。
10. **重建日志。** 清理旧的 `H3String` 对象和指针缓冲，按保存文本构造全新的字符串。禁止调用 `0x4729D0` 重放，因为它会合并行并改时间戳。
11. **重绑活动指针。** 由恢复后的 `currentMonSide/currentMonIndex` 计算 `activeStack`；所有关系向量重新解析为当前槽地址；保留本场 `hero/army/dlg/town/mapitem` 对象。
12. **重算并最终覆盖。** 必要时调用 `0x469330` 重建依赖英雄/军队的派生值，然后再次覆盖快照中的最终士气、运气和法术效果缓存，避免被重算覆盖。
13. **刷新并校验。** 按 `RefreshCreatures @ 0x495770`、`Refresh @ 0x493FC0` 候选顺序刷新，检查数量、位置、格子占用、当前行动方、日志向量和资源引用不变量。校验不通过时禁止继续行动。
14. **提交完成。** 清除待处理加载请求，保留磁盘档和内存列表，解除 UI 锁定。失败则写错误日志并进入安全退出/重新初始化路径，不将半恢复状态交给游戏。

### 1.4 必须保持的不变量

- 每个有效 `(side, slot)` 至多有一个当前槽对象；
- 每个格子占用者都能映射到有效槽，双格部队的两个格状态一致；
- 向量头的 `first/end/capacity` 处于合法范围，元素地址属于当前 BattleMgr 槽区；
- 资源指针属于当前资源管理器，引用计数未被人为减少；
- `+0x514/+0x524` 等双向光环关系没有指向已清空槽；
- 日志向量的每个 `H3String*` 都是新建且仍存活的对象；
- `activeStack`、当前方和 squares 占用信息互相一致。

## 2. 跨会话恢复（第二阶段，原 §7）

跨会话不是第一阶段原型的一部分。设计上采用"战前基线 + 原版重新进入 + 差量恢复"，避免保存旧进程地址：

1. 创建并保存战斗入口标量和同场指纹；不保存旧 BattleMgr、英雄、军队、对话框和资源地址。
2. 另存一份战前战略状态。恢复时先还原基线，再调用目标版本动态确认后的原版 `CALL_BATTLE`（静态候选 `0x4AD160`）重新创建战斗。
3. 新战斗完成原版初始化并进入安全点后，执行第 1 节同场恢复。所有资源、英雄副本和 UI 对象都来自新战斗。
4. 动态验证首回合自动效果、经验、金币、战后结算和 HD 层状态；验证不通过时不开放跨会话读档。

`0x75AE24`、`0x75AEB0`、`0x75ACDD` 属于已有 WoG 扩展代码坐标，不能直接当作目标 SoD 的原版调用点。必须对实际 `Heroes3.exe` 做 xref 和调用约定验证。

## 3. RNG恢复契约（原 16.4）

E/S：`0x50C7C0` 为fastcall(min,max)包装；`0x61842C` 取游戏线程TLS并按32位模运算推进 `seed=seed*0x343FD+0x269EC3`，返回 `(seed>>16)&0x7FFF`。`0x50C7B0` 播种包装同时写镜像与TLS；rand不逐次推进镜像，所以二者不能强制相等。`0x61841F` 为cdecl(seed)，本机 `0x61842B` 指令是普通 `ret`。TLS getter `0x61D8C3` 可能创建线程实例，从辅助线程调用会观测错误线程。

下一步在游戏线程观测seed前后、调用者、范围、返回值、逻辑动作ID和线程；包含初始化、伤害、士气/幸运、AI试算、装饰随机和插件调用。min==max或反向范围是否消耗随机要按分支保留，不能靠结果值推调用次数。纯视觉调用若共用流也会改变后续伤害，不能先验排除。

目标快照带 `rngValid/thread-role/provider-version/currentTLS/seedMirror`；任一来源缺失就拒绝精确恢复。恢复准备/构造/刷新本身可能消费随机：需给这些阶段计数，确定最终种子提交是在重建及所有会消耗随机的刷新后、交回下一动作前；不能先设seed再让Refresh未知消费。此顺序是H级候选，须轨迹验证。多人 `0x50B3C0` 的timeGetTime分支及热座/网络首版排除，第三方独立RNG要独立适配或拒绝。

## 4. 如何恢复内存（原 16.5）

保存是只读快照；恢复是有所有权约束的事务，不是镜像复制。当前允许障碍集合变化的同场恢复：纯预检（包括Before几何、DEF与正反两次追加容量预算）→游戏堆预建完整日志→预解析并持有目标/Before两方向每kind一个DEF引用（从同kind活条目借引用或Load）→原版障碍diff删除/追加/落格→写标量/格子及重算障碍index→交换日志→刷新→提交RNG→重新采集校验。编码不一致则对恢复前快照执行同样的障碍diff、交换旧日志并再次校验；回滚失败或写入中SEH立即停止进程。预建会写游戏分配器，不能宣称绝对零游戏写。以下完整拓扑流程为后续目标，当前不调用资源猜测入口。

1. **Prepare（零游戏写）。** 文件/段CRC、版本/目标/插件集合、战前指纹、代际、主dlg/topdlg、线程、支持场景、安全窗口和完整字段验证。建立目标槽/资源身份及障碍index映射；新文本/资源分配策略要逐对象明确"预建是否本身写资源管理器"，不虚称绝对无副作用。
2. **Acquire。** 进入外层游戏线程安全点，屏蔽玩家动作并阻止插件重入；再次验证上下文。不能在AfterBlt、输入转换、执行器或模态内部直接提交。
3. **Reconcile topology。** 保留42个已构造槽；空→有、有→空、有→异类型分别走已核实原版操作，取得DEF/WAV引用；拆除旧关系/障碍/文本必须先于写入最终格子。任何未支持资源变化在首写前拒绝。
4. **Restore authoritative data。** 写已证白名单，包括info的数值/flags、回合/等待/施法限制/召唤限制、英雄及结算累计；恢复容器元素、关系与障碍资源后，最终覆盖squares及其index映射，避免清理函数把目标格又清掉。
5. **Rebind/rederive。** 身份映射activeStack和关系；只重算证实可派生字段，并按依赖次序覆盖权威效果值。不能调用推进回合/施法/结算接口来"刷新"。
6. **Render/seed/verify。** 用正确ABI重生成战场与侧栏/日志/按钮、完整呈现；验证逻辑、关系/尸体、资源引用和RNG消耗。最终随机提交顺序见本文第 3 节。完成后丢弃本插件过期输入，下一外层帧才恢复控制。
7. **Failure。** 首写前失败正常拒绝；首写后失败不能解除锁并继续战斗，测试阶段立即停止该测试进程/从战略基线重入。正式版需要已经验证的重建/安全退出方案；不得memcpy旧容器头/旧资源地址"回滚"。

## 5. 保存/读档期间的界面处理（原 16.6）

当前链路：`Outside → Ready → Capturing → Ready`；`Ready → RestorePending → Confirming → Preparing → Applying → Verifying → Ready`，失败分为`Rejected`和`FatalPartial`。保存窗口外立即拒绝；读档点击复制记录/指纹/代际，外层消息原函数返回后执行确认，确认返回后再次预检。

- Ready：仅在手动主战场顶层显示悬浮条；原版模态优先，不抢覆盖/输入。既有 `(8,8)/480×24` 布局不变。
- SavePending：记录请求时刻与捕获时刻；档面记录的是捕获时刻，不冒称按键瞬间。按 2026-10-06 裁定不设等待：窗口外静默丢弃，零写、零输入屏蔽；两输入源共享请求ID和down/up序列，改键那次不保存。
- Capturing：同一游戏线程只读，不调用Refresh/重算；取得私有快照后不再引用游戏容器。文件操作是否异步另行设计，后台只能处理私有字节，不能读游戏对象。
- Confirming：普通列表无收起语义；事务busy期间暂停overlay和pending消费，嵌套Choice不得重入保存/恢复。取消不改战斗字段；结束后重新验证主dlg/topdlg、代际、窗口及指纹。
- RestorePending：仅窗口内接受点击，转交下一个外层消息返回边界；到达边界时时机不符即静默取消，不等动画结束。5秒仅作滞留请求的兜底期限，结算/换场也静默取消。提交只在游戏线程、messageDepth==1、executorDepth==0、主dlg顶层、非战术/自动/结束、action==0、spellDepth==0及人类活跃栈窗口（不要求普通刷新动画停止）。此窗口的实机覆盖仍待验收。
